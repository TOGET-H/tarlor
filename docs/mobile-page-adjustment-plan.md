# Mobile Page Adjustment Plan

## Scope

The mobile scan entry should be adjusted into two simple categories:

- Report
- Try-on Results

The screenshot provided by the user is only a structural reference for the try-on result viewport and paging behavior. Do not reuse any brand, product, or system copy from that screenshot.

## Entry

Keep the mobile entry under the existing mobile route.

- `/mobile` opens the mobile experience.
- `/mobile?tab=report&status=ready` can directly open the report tab.
- `/mobile?tab=result` can directly open the try-on result tab.
- Existing `/mobile/result` should remain compatible and open the try-on result tab.

## Shared Mobile Shell

The top area should be lightweight and project-specific.

- Provide two category tabs: `报告` and `试穿结果`.
- Use this project's own naming and wording only.
- Do not show the screenshot's brand, system name, or related copy.
- Keep the layout simple and suitable for phone scanning scenarios.
- The mobile page should not provide an in-page theme switcher.
- Mobile theme should be controlled by URL parameter:
  - `theme=classic`
  - `theme=monochrome`
  - `theme=tech`
- Invalid or missing theme parameters should fall back to `classic`.
- The mobile root should apply the same theme class naming as PC so existing PC theme variables can be reused.
- QR links generated by the PC terminal should eventually include the current theme parameter.
- Report content color swatches should keep their actual report colors and should not be theme-filtered.

## Report Tab

The report page should be a simple vertical long page.

Requirements:

- It is scrollable vertically.
- It should not use a cover section.
- It should not provide save-long-image actions.
- It should not provide report download actions.
- It should open directly into report content.
- Content should be concise and easier to read on phones.
- Use text, images, and color swatches.
- The report should be the mobile rearrangement of the PC report, not a separate simplified report.
- The `基础特征` section must align with the PC report's currently rendered content, not the older summary `diagnosis` data.
- PC currently renders `featureProfileCards + SkinToneCard` for `基础特征`; mobile should rearrange that content vertically.

Suggested content order:

1. `基础特征`
   - Use the PC report's two image feature cards:
     - `体型：X型沙漏曲线`
     - `脸型：圆形脸温柔款`
   - Use the PC report's skin tone card:
     - `肤色：春季型肤色`
     - `人体色特征`
     - `色彩适配原则`
     - `推荐用色`
   - Keep titles, ordering, and conclusions aligned with the PC report.

2. `风格定位`
   - `推荐色彩` belongs inside `风格定位`; it should not be a separate top-level mobile section.
   - Do not show generic color ratio rules on PC or mobile, including copy such as `建议全身色彩不超过 3 种，主色占 70%、辅助色 25%、点缀色 5%。`.
   - The mobile style section should match the PC style section structure:
     - Core style label and value: `你的核心风格` / `优雅休闲风`
     - Style tags: `轻甜气质`, `日常休闲`, `柔和低饱和`
     - Core elements: `色彩`, `版型`, `面料`, `配饰`
     - Recommended colors: `浅灰`, `卡其`, `浅蓝`, `米白`
     - Occasion: `日常休闲（逛街 / 咖啡 / 短途出行）` plus the PC explanation.
   - Do not add a separate `领型` row unless the PC report also adds it.
   - Do not add a separate `搭配公式` section unless the PC report also adds it.
   - The mobile style verdict should be redesigned as a clear conclusion block:
     - Small label: `你的核心风格`
     - Large main value: `优雅休闲风`
     - Three chip tags below: `轻甜气质`, `日常休闲`, `柔和低饱和`
   - Avoid rendering the style verdict as a cramped inline sentence.

3. `推荐搭配`
   - Use this project's outfit or product images.
   - Add short reasons for each recommendation.

4. `穿搭建议`
   - Match the PC section title and content.
   - Use two cards in PC order:
     - `细节优化技巧`
     - `需要避开的单品`
   - Each row should include the same item title and reason copy as the PC report.
   - Do not reduce this section to title-only lists.
   - Mobile rows can use compact numbering for better scanning.

## Try-on Results Tab

The try-on result page should follow the screenshot only in page structure and paging interaction.

Structure:

- Project-specific lightweight header.
- One large central result viewport.
- Show one generated image or video item at a time.
- Left and right arrow controls.
- Current index text, such as `第 1 / N 张`.
- A `下载图片` button for downloadable image items.
- The result card should not show a right-side item title such as `轻通勤针织上装`.
- The result card should not repeat the brand name inside the card when the page header already shows it.
- Keep the card header simple, such as `本次生成结果`.

Paging behavior:

- Results are displayed from a result array in order.
- The left arrow goes to the previous item.
- The right arrow goes to the next item.
- Disable the left arrow on the first item.
- Disable the right arrow on the last item.
- Add a subtle transition if it does not complicate the implementation.

Copy rules:

- Use this project's own wording, such as `AI 试穿结果`, `本次生成结果`, and `下载图片`.
- Do not use any brand or wording from the reference screenshot.
- For video items, show project-appropriate video copy.
- For loading items, show a clear generation state.

## Data Structure Direction

Separate the mobile data into two groups so future real scan payloads can replace demo data cleanly.

- `mobileReportData`
- `mobileTryOnResults`

The UI should be data-driven where practical, instead of hardcoding every card directly in the component.
